版本控制的介紹

  • 版本控制是什麼?
    如果你有唸過大學，那麼你一定有用word寫報告的經驗。
    令人難以忘懷、耗費很多心力、佔學期成績至少40%，
    而且在繳交截止日前，還要熬幾個夜晚才能完成的報告就是期末報告XD
    有些人可能會這樣做，
    每修改一次報告(XXX.doc)就另存新檔並變更檔名(目的是保留每一次更改的紀錄)，
    直至完成最終版本的報告時，就會有數個不同檔名的報告(可視為數個不同版本的報告)。
    如果我們將報告視為一種檔案，我們就會有數個不同版本的檔案。
    爾後如果我們想查看某一次變更的檔案內容，我們就可以直接查閱對應版本的檔案；
    如果我們想將某一次變更的檔案再度翻新，我們就不再需要花費更多的時間重從零開始建立檔案。
    簡言之，如果一個檔案有數個不同的版本，我們也將每一個版本的檔案保存起來(方便之後查閱或修改)，
    這就是版本控制的基礎概念。

  • 為什麼要用版本控制軟體？
    目的就是解決檔案數量過多或產品開發衍生的問題
    For個人檔案管理：隨著時間的推移，檔案的數量愈來愈多，進而導致檔案管理變得不易 。
    For團隊分支(Branch)管理：若PM臨時有緊急修復bug的需求，工程師團隊必須先還原當下最新版本的專案(新功尚未正式對外發布)並且debug，進而導致耗費冗長的修復時間。

看穿Git(一種版本控制軟體)的把戲 - 人工版本控制的5種概念

  • 假設某一個工作目錄下有一個專案(有3個檔案，檔案之間互相依賴。)
  • 1.建立新版本的專案：先建立一個新資料夾，取名為版本序號，然後複製3個原有的專案檔案，接著將它們拉進資料夾內，最後進行修改及儲存。
  • 2.不加入版本控制的檔案：將該檔案(隱藏檔案、設定檔案等等)保留在工作目錄之下，不將其加入爾後每一次的新版本資料夾。
  • 3.避免版本號衝突(共用的工作目錄)：每個人都可以至共用的工作目錄取用最新版本的專案資料夾(假設取名為V3)進行修改，此時如果每個人將專案資料夾取名為V4，那麼上傳至共用的工作目錄之下會發生命名衝突(資料夾迭代)，導致沒有辦法保存每個人修改過的專案。
    為了解決這個問題，我們可以採取絕對不會重複的命名方式(如：亂數)，確保每個人修改的最新版專案都可以上傳至共用的工作目錄。
  • 4.最新的修改版本：建立一個名為Newest的資料夾，將最新修改的專案資料夾移至該資料夾。
  • 5.版本的修改紀錄與順序：建立一個名為Order資料夾，將所有修改的專案資料夾移至該資料夾，並以修改時間排序。

Git基本操作指令

  • 1.一元復始：git init(initialize的簡寫)
  • (1)初始化(initialize)當下的工作目錄，使得Git對該目錄進行版控。
  • (2)假設終端機的位置在當下的工作目錄，若你在提示符後面輸入git init並按Enter執行，Git會在該目錄下會建立一個名為「.git」的隱藏資料夾，資料夾的內容是版控所需的預設檔案。可以用指令ls -al查看所有檔案資訊。
  • (3)若你在提示符後面輸入rm -rf .git並按Enter執行，即可解除Git對工作目錄的版控初始化，使工作目錄脫離版本控制並刪除Git的隱藏資料夾。
  • 2.你目前的狀態如何?：git status
  • (1)(假設終端機的位置在當下的工作目錄，)若你在提示符後面輸入git status並按Enter執行，終端機會顯示當下該目錄內檔案的狀態資訊。
    PS : 之後每一個指令的操作說明都會省略「假設終端機的位置在當下的工作目錄，」。
  • (2)查看當下工作目錄中所有檔案的狀態，一共有四種，如下所述。
    • Nothing to commit, working tree clean：表示目前沒有任何未提交的變動，工作目錄非常乾淨。
    • Untracked files：找到新檔案。若你要將其加入版本控制的名單(暫存區)，請執行 git add 檔案名稱.副檔名 。
    • Changes not staged for commit：檔案被修改了。若你要將其加入暫存區，請執行 git add 檔案名稱.副檔名。
    • Changes to be committed：檔案被送進暫存區。若你要提交，請執行 git commit -m "提交說明"。
  • 3.選我選我選我：git add
  • (1)將(未加入版本控制的)某一個檔案(新檔案或是修改後的檔案)或資料夾(新資料夾或是修改後的資料夾)加入版本控制的名單(暫存區)
  • (2)若你在提示符後面輸入git add 檔案名稱. 副檔名(git add 資料夾名稱)並按Enter執行，Git就會將該檔案(資料夾)加入暫存區；
    反之，若你在提示符後面輸入git rm --cached 檔案名稱. 副檔名(git rm --cached 資料夾名稱)並按Enter執行，Git就會將該檔案(資料夾)從暫存區剔除。
  • (3)承上，接著可以執行git status查看當前檔案的狀態，「 Changes to be committed : 」的下方會顯示「加入版控的檔案(新的或是修改後的)」，以「 modified: 檔案名稱.副檔名 」表示[若該(新的或是修改後的)檔案是”第一次”加入版控，以「 new file: 檔案名稱.副檔名 」表示。]；而「 Untracked files : 」的下方會顯示「未加入版控的檔案清單」。
  • (4)若你想將工作目錄下的所有檔案加入版控的檔案清單，可以執行git add . ；
    反之，可以執行git rm --cached -r . ，即可將加入版控的所有檔案從名單中剔除。
  • 4.把你寫進我的故事裡：git commit
  • (1)將變更的檔案加入版控之後，若你在提示符後面輸入git commit 檔案名稱. 副檔名並按Enter執行，Git就會將該檔案建立一個新的版本紀錄，接著會跳出Vim的視窗，然後在裡面輸入文字訊息(commit message)，說明本次變更的內容及原因，最後按「:q」即可退出Vim。
  • (2)若於上一個步驟中，你沒有在Vim裡面輸入文字訊息並退出Vim，在提示符後面就會顯示「Aborting commit due to empty commit message.」。
    接著可以在提示符後面輸入git commit -m “文字訊息“，在提示符後面就會顯示建立新版本的檔案。
    補充說明：「git commit -am “文字訊息”」該指令是指可以把「已被追蹤的檔案」加入暫存區並直接提交出去。若你只修改被追蹤的檔案，可以直接使用該指令 ; 若你有新加入的檔案，要先將其加入暫存區，才能使用該指令。
  • 5.歷史記錄一目了然：git log
  • (1)承上，若你在提示符後面輸入git log並按Enter執行，終端機就會顯示先前每一次變更檔案時輸入的文字訊息(每一次變更檔案的紀錄[ 以亂序英數字串當作每一次的變更ID ]、作者和變更時間)。按Ｑ即可退出。
  • (2)若你只想查看簡短的變更紀錄，可以在提示符後面輸入git log —oneline並按Enter執行，終端機就會顯示簡短的歷史紀錄，每一個歷史紀錄以變更ID的前7碼和文字訊息表示。
    補充說明：一般而言，在進入版控狀態的工作目錄內都是先修改檔案和加入新的相依檔案，再將這些檔案加入(add)暫存區，最後將其提交(commit)建立一個新的歷史紀錄。
    以人工版控來比喻的話，該程序就好像每作一次變更檔案，就將這些檔案放入一個名為變更ID的資料夾內。

  • 6.我想回到過去：git checkout
    若你在提示符後面輸入git checkout 變更ID(某一次變更紀錄對應的亂序英數字串)並按Enter執行，你就可以回到某一個檔案先前某一次的變更紀錄(某一個舊版本的檔案)。
    此時歷史紀錄中最新的(最上面的)變更紀錄就是先前某一次的變更紀錄。
    反之，若你想返回該檔案最近一次的變更紀錄(最新版本的檔案)，可以在提示符後面輸入git checkout master(回到master[ 預設的主要分支 ]的最新版本)。
    以人工版控來比喻的話，該程序就好像從某一個名為變更ID的資料夾跳到另一個名為變更ID的資料夾。

  • 7.不重要的邊緣人：.gitignore

  • (1)若在工作目錄中有不需要進行版控的檔案或資料夾(尚未被追蹤的檔案[Untracked files])，那麼可以先建立一個純文字檔「.gitignore」(在提示符後面輸入touch .gitignore)，接著用終端機內建文字編輯器(vim)或是其他文字編輯器(如VS code)將不需要進行版控的檔案或資料夾以「忽略規則的語法」寫入其中並儲存。之後用git status查看檔案或資料夾的狀態時，.gitignore就會出在Untracked files裡面。
  • (2)一般而言，「.gitignore」也會加入版控的名單裡面，因為要讓自己或其他經手該工作目錄的人知道有哪些檔案不需要版控。
  • 8.哪裡不一樣：git diff

  • (1)假設在工作目錄進行版控初始化之後，將原本的工作目錄加入版控的行列並提交(建立初始版本紀錄)。
    第一次修改該檔案並儲存之後，若在提示符後面輸入git diff並按Enter執行，可以查看該檔案的「第一次修改的內容(增加和減少的內容會以不同顏色顯示)」。
    接著將第一次修改後的工作目錄加入版控的行列並提交(第一次變更)。
    後續在每一次修改檔案(第2次修改檔案、第3次修改檔案…)之後，並將其加入版控行列之前，都可以使用「git diff」查看每一次修改的變更內容。
    EX : 第3次修改html檔之後，用「git diff」查看修改的內容正是「增加了」。

  • (2)假設在工作目錄進行版控初始化之後，除了有初始版本的紀錄(第1次commit)之外，你至少有1個後續建立的commit[ 至少有兩個commit ]。
    在第n次修改檔案之後，若在提示符後面輸入git diff “第k次commit ID 前8位字串”並按Enter執行，
    可以查看「第n次修改後的檔案和第k次commit的差異(增加和減少的內容會以不同顏色顯示)」，n,k皆為正整數且n>=k。
    EX : 第3次修改的html檔之後，用「git diff 3d8b928f(第2次commit ID 前8位字串)」查看
    「第3次修改後的html檔和第2次commit的差異」是「增加了和」。

  • (3)假設在工作目錄進行版控初始化之後，除了有初始版本的紀錄(commit)之外，你至少有1個後續建立的commit[ 至少有兩個commit ]。
    在第n次修改檔案並加入版控行列之後，若在提示符後面輸入git diff --cached(或是--staged) “第k次commit ID 前8位字串”並按Enter執行，
    可以查看「第n次修改檔案並加入版控行列之後的檔案和第k次commit的差異(增加和減少的內容會以不同顏色顯示)」，n,k皆為正整數且n>=k。
    EX : 第4次修改html檔並加入版控行列之後，用「git diff --cached 81d07f65f(第3次commit ID 前8位字串)」查看
    「第4次修改後的html檔和第3次commit的差異」是「增加了和」。

  • (4)假設在工作目錄進行版控初始化之後，除了有初始版本的紀錄(commit)之外，你至少有1個後續建立的commit[ 至少有兩個commit ]。
    若在提示符後面輸入git diff “第m次commit ID 前8位字串” “第n次commit ID 前8位字串”並按Enter執行，
    可以查看「第m次commit和第n次commit的差異(增加和減少的內容會以不同顏色顯示)」，n,m皆為正整數且n>m。
    EX : 用「git diff 3d8b928f(第2次commit ID 前8位字串) HEAD(第5次[ 最新的 ]的commit ID 前8位字串)」查看
    「第2次commit和第5次(最新的)commit的差異」是「增加了、和」。
    補充說明：終端機進入git log畫面之後，因為HEAD是最新的commit ID的代名詞，所以「最新的commit ID 前8位字串」可以用「HEAD」取代。

Git一般操作程序

  • 1.將專案目錄初始化(git init)
  • 2.查看檔案的狀態(git status)
  • 3.建立「.gitignore」，用文字編輯器開啟該檔案，將無需被版控的檔案寫進去。
  • 4.查看檔案的狀態(git status)，確認是否還有該忽略(不需要被版控)的檔案。
  • 5.將所有檔案(包含「.gitignore」)加入版本控制的名單(git add)
  • 6.建立第一個提交(git commit -am “1st commit message”)
    上述4個步驟，即可建立初始版本的專案，然後在此基礎上繼續開發專案。
  • 7.如果有新檔案納入，必須將其加入版本控制的名單(git add 檔案名稱.副檔名)。
  • 8.當專案進行到一個階段時，可以使用「git diff的相關指令」查看修改內容，之後即可建立第二個提交(git commit -am “2nd commit message”)…

Git的平行時空 : Branch(分支)

  • 1.為什麼需要branch?
    假設你開發的產品目前有一個已發佈(commit)的穩定版本，並且你是使用「單一生產線的模式」進行開發。
    如果你在新功能開發至一半的時候，又發現產品有新的bug，那麼以單一產線開發的方式進行新功能開發和debug，而且要在有限的時間內完成這兩件事幾乎是Ｍission Impossible！

  • 2.簡易說明新建分支與合併分支
    假設主分支(main)旗下有一個初始專案(init)，初始專案被我更改之後變成一個提交(main-commit-1)，此時我的主分支旗下有init和main-commit-1。
    在main的基礎上，我又創建了一個新分支(new-feature)[ 旗下有init、main-commit-1 ]，main-commit-1被我更改之後變成一個提交(new-feature-commit-1)，
    new-feature-commit-1又被我更改之後變成了一個提交(new-feature-commit-2)，此時我的分支旗下有init、main-commit-1、new-feature-commit-1和new-feature-commit-2。
    又因為new-feature-commit-2是由init演變而來，所以這幾個commit有迭代更改的關係，因此最後我要將主分支和新分支合併(merge)的時候，
    我只需要將 new-feature-commit-1 和 new-feature-commit-2 納入 main 的旗下即可。

Git Branch基本操作指令

  • 1.給我一個新的宇宙：git branch
  • (1)使用Git初始化工作目錄之後，執行第一次commit，同時Git也會自動生成主分支(master)。
  • (2)有了第一個commit之後，若你想建立一個名為name的分支，可以在提示符後面輸入git branch “name”並按Enter執行。
  • (3)若你想查看當下所有的分支[ 主分支(master)和其他分支 ]，可以在提示符後面輸入git branch -v並按Enter執行。
  • (4)若你想刪掉名為name的分支，可以在提示符後面輸入git branch -d “name”並按Enter執行。

  • 2.穿梭至另一個宇宙：git checkout
    假設你有兩個分支(master & new-feature)，而且目前Git是位於master。
    若你想切換至另一個分支(new-feature)，可以在提示符後面輸入git checkout new-feature並按Enter執行。

  • 3.當兩個宇宙合併：git merge
    假設你有兩個分支(master & new-feature)，而且目前Git是位於master。
    若你想將另一個分支(new-feature)抓進所在分支(master)裡合併，可以在提示符後面輸入git merge new-feature並按Enter執行。
    接著查看目前的狀態(git status)，就會看到最新的commit是master，然後可以將new-feature這個分支刪除(git branch -d “new-feature”)。

  • 4.Git : 「當衝突(Conflict)發生時，我沒辦法處理喔!」
    假設某一個專案目前有兩個分支(master & new-feature)，你目前的Git是位於master，而你的另一位同事位於new-feature。
    若你們剛好都有改到同一個檔案內的同一行程式碼，那麼兩個分支就會產生衝突，也無法進行合併(merge)。
    當有衝突時，我們要先手動更改發生衝突的地方(一般的做法是選擇其中一個版本或是改成第三種版本)，才可以順利合併。

線上軟體原始碼代管服務平台 : Github

  • Github是什麼? :
    Github是一個可視化管理與共享Repository(簡稱為Repo，中譯為倉儲或儲存庫。)的線上軟體原始碼代管服務平台，使用Git作為版本控制的軟體，
    其中Repo是指”被Git控制的“專案目錄(專案資料夾)。

    我們寫的程式碼就好像我們用積木設計遊戲製作出的積木成品(比如積木城堡) 。
    Github就好像線上積木展示櫃，我們可以將自己的積木城堡放上去向其他人展示，也可以在上面欣賞別人的積木城堡。
    如果覺得別人的積木城堡很棒，我們不但可以給予評論和點讚，也可以將它取下來自行研究，甚至可以改造別人的積木城堡(比如新蓋屋頂)。
    別人如果滿意我們改造後的城堡，可以將它放在自己的線上積木展示櫃。
    Git就好像時光倒流相機，在線上展示之前，如果我們想紀錄製作的過程，我們可以用照相機拍攝未完成的積木城堡並放在線上展示櫃裡向其他人展示。
    在完成積木城堡之後，如果我們做錯了城堡的屋頂或是想變成另一種風格的屋頂，我們可以用照相機回到過去某一個製作過程重新設計屋頂。
    也因為我們有城堡製作的紀錄，所以我們不用擔心別人可能會改壞我們的城堡，別人一但改壞城堡結構，他可以重新取下改造前的城堡再次改造，也不會影響我們完工的積木城堡。

遠端共同協作操作指令(使用GitHub)

  • 1.我就是潮流 git push

  • (1)使用終端機「將本地(電腦)中的一個Repository」(push an existing repository from the command line) 或「在GitHub新建一個Repository」(create a new repository on the command line) 推(上傳)至遠端Git伺服器，
    也就是「將專案目錄(包含所有歷史提交和分支)由本地上傳至遠端Git伺服器」。

  • (2)「 create a new repository on the command line 」下方的指令內容與「你在本地新建一個Repository(前述的Git操作程序)」的指令內容差異不大，
    比較不一樣的地方是第一行指令「 echo "# Repo名稱” >> README.md 」，該指令的意思是『 建立一個叫做 「README.md」 的檔案，並在裡面寫入 「# Repo名稱」 這個專案標題。』。
    為何需要這一行指令? 因為你建立的專案目錄至少要有一個檔案才能進行提交(commit)，而這裡用的檔案是一個md(markdown)檔。
    也因為「在GitHub新建一個Repository」的操作方式與「前述的Git操作程序」差異不大，所以這邊只說明三個共同的指令。

  • git remote add origin git@github.com:Sam16888/Git101-practice.git

  • 新增一個遠端伺服器，取名為 origin(可自取名稱)，位置是在 GitHub 上新建一個Repository的專屬網址 「 git@github.com:Sam16888/Git101-practice.git 」。
    以後你只要在指令中輸入 origin，Git 就會自動代入後面那一長串的 GitHub 網址，不用每次都要複製貼上。
    PS:為何我不選擇使用HTTPS連線協定，而是使用SSH連線協定(要先在 GitHub 上設定過 SSH Key才可以使用)當作遠端伺服器的位置？
    在2021/08/13以前，如果我使用HTTPS連線協定作為遠端伺服器的位置，那麼我無論是上傳(或下載)程式碼時，都要輸入GitHub的帳號和密碼，頗為麻煩。
    在2021/08/13(含)以後，因為GitHub放棄使用「 password authentication 」的認證方式，改為使用「 Personal Access Token(PAT)[ 中譯為個人訪問令牌 ] 」的認證方式， 所以用戶無法像以前透過輸入帳號和密碼的方式上傳資料，而是要使用PAT的認證方式上傳資料，程序上更麻煩XD
    至於要如何使用PAT的認證方式上傳資料，有興趣的人可以自己去問AI。

  • git branch -M main

  • 將本地(電腦)主分支Master強制改名為main。
    如果你已經將本地主分支Master改名為main，就可以省略這一行指令。
    至於要怎麼改呢？
    使用終端機進入專案目錄後，先執行該指令「 git config --global init.defaultBranch main 」
    ，接著執行版控初始化，以後你本地主分支的名字就會變成main。
    PS : 為響應黑人平權運動，GitHub宣布從2020年10月1日起改變新Git儲存庫的預設命名，以main來取代原本的master。

  • git push -u origin main

  • 將本地主分支(main)推送至origin這個遠端伺服器。
    若origin無分支，那麼會新建一個名為main的主分支並生成一個commit ; 若origin有主分支(mian)，那麼會生成一個最新的commit。
    其中「-u (或 --set-upstream)」的意思是設定上游(追蹤)關係。
    也因為這是一個「一勞永逸」的參數，所以第一次執行該指令時加上 -u，Git 就會記住「你的本地主分支(main) 以後都要對應到 origin 的主分支(main)。」

  • (3)實際操作(使用終端機「將本地的一個Repository」push至遠端Git伺服器)：

  • 步驟1 : 先在GitHub新建一個Repository(我沒有加入README)，取名為Git101-practice。

  • 步驟2 : 打開終端機，將電腦中的專案目錄執行版控初始化，接著選定檔案加入版控。

  • 步驟3 : 執行第一次commit，將上一步驟建立的專案目錄推(上傳)至遠端Git伺服器的Git101-practice。


  • 步驟4 : 將本地的一個Repo推送(上傳)至遠端Git伺服器之後，假設終端機沒有關掉且仍是位於版控狀態之下的專案目錄。
    當你改了檔案(我是改html檔)並且完成第二次commit之後，若想進行第二次push，那麼只需執行「 git push (-u) origin main 」即可。
    完成第二次push之後，commit的數量會變成2，點進去之後你就可以查看每一個commit的紀錄。


  • 2.跟隨潮流 git pull

  • (1)將Repository的最新commit(最新變動)由遠端Git伺服器下載至本地。
    承接上一步驟(git push)，若GitHub上的專案資料夾在main分支有最新的commit(你在本地執行git push或是在GitHub進行修改都會產生最新的commit)，而且你的終端機也位於版控狀態下main分支的專案資料夾，
    那麼你可以用「git pull origin main」下載新的commit至你的專案資料夾，也就是將遠端(origin)的main分支抓進本地的main分支裡合併(merge)。
    由此可知，順利git pull的條件是「遠端Git伺服器的commit數量比本地的commit數量還要多」。
    如果該條件不成立，你就無法順利git pull。此時你可能要先完成「解決遠端(origin)的main分支和本地的main分支發生的衝突(conflict)」、「執行git push」或是其他前置作業，才能順利git pull。

  • (2)實際操作(承接Git push實際操作的第四個步驟)：

  • 步驟1 : 前往GitHub中的Git101-practice，選擇某一個檔案進行變更(我是改html檔)，然後執行第三次commit。
    此時遠端Git伺服器的Repo比你電腦上的Repo多了一個commit。

  • 步驟2 : 回到終端機，將GitHub中Repo拉(下載)至本地。此時本地的Repo會新增第三次commit，就會和遠端Git伺服器的Repo會一模一樣。


  • 步驟3 : 承接上一步驟，因為我想刻意製造衝突(Conflict)，看後續會發生什麼事情，所以我先在本地變更html檔(加了)，接著執行第四次commit(3rd change)
    ; 在GitHub的Git101-practice變更了html檔(加了)，接著執行第四次commit(3rd change)。


然後我執行「git pull origin main」，以下是後續遇到的情況：

  • 步驟4 : 本地分支和遠端Git分支出現分歧(顯示訊息fatal: Need to specify how to reconcile divergent branches.)

  • 步驟5 : 解決分歧。我選用的方法是 Merge，執行git config pull.rebase false，該方法可以保留本地分支和遠端Git分支的變更[兩個不同作者的3rd change提交]。

參考資料：
1.Git Pull 策略完全指南
2.解決 git pull 錯誤

  • 步驟6 : 重新執行「git pull origin main」
  • 步驟7 : 化解衝突[ 我接受來源變更(在GitHub上的變更，而不是本機的變更。) ]，並建立新的commit(4th change)。


  • 步驟8 : 執行「git push origin main」，將本地最新的commit推至遠端Git伺服器。


  • 3.抓到你了git clone
  • (1)將Github上的某一個開源專案下載至本地(電腦)，儲存於終端機當下的工作位置。
  • (2)實際操作
    步驟1 : 打開終端機將工作位置移至你想下載開源專案的位置
    步驟2 : 打開瀏覽器，前往開源專案的GitHub頁面，頁面右上角有一個綠色按鈕(< > code)，點擊之後會預設顯示Local，下方有三種clone的方式。
    如果不想用終端機下載專案，也可以直接下載ZIP壓縮檔至目的地。
    步驟3 : 複製連結 HTTPS 或 SSH
    步驟4 : 在終端機執行「git clone 複製的連結」，即可將開源專案(包含所有歷史提交和分支)下載至本地並存放於當下的工作位置。
    PS :「 git clone 」與「 git pull 」的差異：
    「 git clone 」適用於初次下載本地沒有的專案(包含所有歷史提交和分支)，
    「 git pull 」適用於下載本地已有的專案更新(遠端伺服器的專案更新)並將其合併至至本地的同名分支。

早在3月初的時候，我已經剛看了40%的鋰學院ＧIT101教學影片。
為何會拖到7月中才看完全部的課程？

3月中的時候，開始忙搬家的事情，一直忙到4月中。
4月中的時候，重新看一遍前40%的課程影片和自己的寫的筆記。
5月初的時後，我離職並開始過著每天看pressplay的線上課程-終極學習系統(搬家之前，有優惠時所購買。)和準備第8屆WeHelp的申請作業，一直忙到月底。
6月初ＷeHelp培訓開始，在第一週(試水溫)之後，因為我覺得他們的培訓方式不太適合我(我認為高壓的學習環境完全無法使我的學習模式符合終極學習系統的核心精神)
，所以我決定退訓，改以完全自學的方式準備轉職。

退訓之後，我開始接續看終極學習系統和ＧIT101後面60%的課程，預計７月底前看完這兩個課程並擬定初步的學習計劃，然後於8月初開始執行轉職自學計劃。
直至7月中我才看完ＧIT101的教學影片，目前只剩下終極學習系統最後兩週的課程。

對於非本科準備轉職軟體工程師的人而言，我很推薦ＧIT101這一堂課(雖然有點課程影片有點舊XD)，因為這一堂課本身就是為初學者設計的。
如果你願意搭配我寫的這一篇貼文學習，你應該沒有道理學不會XD
比較需要注意的地方是有些情境是要在「多人協作的時候」才有可能發生，自己一個人比較難模擬出這樣的情境。
這一部分的內容先大致了解即可，等你以後實際遇到各種情境的時候再去了解與學習即可。

Git其實和HTML&CSS一樣，易學難精，這一門課教的內容只是一小部分，但對於初學者而言非常足夠。
如果你覺得Git很有趣，也想學得更深入、更完整，這件事可以等到你轉職為前後端工程師之後再進行(我就是這樣想的)。
